ReEvo — the LLM writes the heuristic, evolution scores it

One reframe carries the whole paper: the search does not run over solutions to your problem — it runs over programs, small pieces of heuristic code, and the best program is the product.

1. The reframe: a search over programs

A hyper-heuristic is a search one level up: instead of searching the space of solutions (teams, tours, decks), it searches the space of heuristics — the rules that guide a lower-level search. ReEvo's version uses an LLM as the thing that produces candidate heuristics, which the paper names Language Hyper-Heuristics: an emerging variant of Hyper-Heuristics that leverages LLMs for heuristic generation, featuring minimal manual intervention and open-ended heuristic spaces. "Open-ended" is the point — a classical hyper-heuristic recombines operators from a fixed hand-built menu; an LLM can write code nobody put on any menu.

Concretely, each individual in the population is a short Python function (in the 🟢 repo, literally the file gpt.py): a penalty function for guided local search, a desirability measure for ant colony optimization, a scoring rule for a constructive builder. In your application, an individual is a team filter — code that reads one team and returns keep/skip or a penalty number.

2. The two LLM roles

roleinputoutput
generatortask specification, parent heuristics, reflectionsa new heuristic — runnable code
reflectortwo parent heuristics + which one scored bettera verbal analysis of why — text, not code

The paper's phrase for the reflector's output is verbal gradients: a novel integration of evolutionary search for efficiently exploring the heuristic space, and LLM reflections to provide verbal gradients within the space. Where gradient descent asks "in which numeric direction does the score improve?", ReEvo asks the reflector "in which describable direction?" — and feeds the answer into the next generation's prompt.

3. The five-step loop

  1. Initialize. ReEvo initializes a heuristic population by prompting the generator LLM with a task specification. The specification holds the problem description (if any), what the heuristic must do, and its function signature.
  2. Select parents. Random pairs among heuristics that run without crashing, while avoiding pairing heuristics with an identical meta-objective value — a pair with equal scores gives the reflector nothing to explain.
  3. Reflect (short-term). The reflector compares the pair — told explicitly which performed better — and writes the why.
  4. Crossover. The generator writes an offspring given task specifications, a pair of parent heuristics, explicit indications of their relative performance, short-term reflections over the pair, and generation instructions.
  5. Reflect (long-term) + elitist mutation. The reflector given previous long-term reflections and newly gained short-term ones, summarizes them and gives hints for improved heuristic design; then based on long-term reflections, the generator LLM samples multiple heuristics to improve the current best one. Short-term reflection is per-pair and local; long-term reflection is the accumulated cross-generation memory.

4. The meta-objective — where your idea plugs in

What scores an individual: The meta-objective function F is the expected performance of a heuristic h for certain COP. It is estimated by the average performance on a dataset of problem instances. Mechanically the repo just runs the candidate code and reads the score off stdout. Everything rides on that instance dataset being cheap to evaluate — ReEvo's benchmarks (TSP, CVRP, orienteering, knapsack, bin packing, chip decap placement, across five heterogeneous algorithmic types) all score a candidate in milliseconds-to-seconds.

That is exactly why your pruning-rule application fits and the "evolve the whole team-builder" application did not. Your meta-objective for a filter, in one line:

F(rule) = weighted share of ranked top teams the rule keeps (weight falling with placement, e.g. 1/rank) × share of sampled teams it prunes — every term a membership check, zero battles.

On that last row: ReEvo's black-box mode (no problem description, score feedback only) exists for domains the LLM cannot describe. VGC is the opposite case — the generator can propose domain-aware rules ("every team needs speed control") no blind mutation would find. The white-box setting is your advantage; take it.

5. Claims to carry with the right size

The headline — ReEvo yields state-of-the-art and competitive meta-heuristics, evolutionary algorithms, heuristics, and neural solvers, while being more sample-efficient than prior LHHs — is against FunSearch and EoH, on cheap-evaluation benchmarks, and "sample-efficient" means fewer LLM-generated candidates to reach a given score. Two honest limits for your case: nothing in the paper touches games or team selection (verified — no such domain appears in paper, repo, or project page), and every benchmark has the cheap evaluator you only get by choosing the pruning-rule application. The paper earns the loop; your scoring design earns the fit.
