# Masked fine tuning configuration and structural cost

## Which entry points configure masked fine tuning?

### Takeaway
The LLaDA and Dream supervised fine tuning examples share one masked loss evaluation per microbatch. Dream changes logit alignment, weighting, and response cropping. A low rank adapter is optional; the unquantized nonadapter path is the full parameter route. These are source observations, not tested configurations.

### Cited findings
- Audit pin: `ZHZisZZ/dllm` commit `ca176752fbceec49c6b4777a2c18ae88e4eb10ed`. LLaDA's entry point parses model/data/training dataclasses, loads model/tokenizer, maps chat messages, postprocesses lengths, constructs `MDLMTrainer` with train and test splits, calls training, and saves model/tokenizer. [LLaDA entry point, lines 67–125](https://github.com/ZHZisZZ/dllm/blob/ca176752fbceec49c6b4777a2c18ae88e4eb10ed/examples/llada/sft.py#L67-L125).
- LLaDA's example defaults to `GSAI-ML/LLaDA-8B-Base`, prompt loss masking enabled, five epochs, learning rate `2e-5`, per-device train/eval batch four, and length grouping. These example defaults are not recommendations for the Pokémon dataset. [LLaDA arguments, lines 42–64](https://github.com/ZHZisZZ/dllm/blob/ca176752fbceec49c6b4777a2c18ae88e4eb10ed/examples/llada/sft.py#L42-L64).
- Dream's example instead selects `Dream-org/Dream-v0-Base-7B`, enables per-batch response cropping, uses `DreamTrainer` and `DreamSFTCollator`, and keeps custom dataset columns. [Dream arguments, lines 43–96](https://github.com/ZHZisZZ/dllm/blob/ca176752fbceec49c6b4777a2c18ae88e4eb10ed/examples/dream/sft.py#L43-L96), [setup, lines 99–151](https://github.com/ZHZisZZ/dllm/blob/ca176752fbceec49c6b4777a2c18ae88e4eb10ed/examples/dream/sft.py#L99-L151).
- `DreamTrainer` subclasses `MDLMTrainer`. It forces right-shifted logits and defaults to `cart[geo_p:0.3]` weighting. CART constructs a distance-based geometric matrix and multiplies it by the unmasked-position indicator. It does not call the model for clean targets or a second forward pass. [Dream trainer, lines 9–77](https://github.com/ZHZisZZ/dllm/blob/ca176752fbceec49c6b4777a2c18ae88e4eb10ed/dllm/pipelines/dream/trainer.py#L9-L77), [shared single model call, lines 149–192](https://github.com/ZHZisZZ/dllm/blob/ca176752fbceec49c6b4777a2c18ae88e4eb10ed/dllm/core/trainers/mdlm.py#L149-L192).
- The masked autoregressive-to-diffusion example `examples/a2d/mdlm/sft.py` also instantiates `MDLMTrainer`, but points to a local converted `Qwen3-0.6B` model. The encoder example points to `answerdotai/ModernBERT-large` and the same trainer. Neither should be confused with block `examples/a2d/bd3lm/sft.py`. [Converted-model arguments and trainer, lines 41–119](https://github.com/ZHZisZZ/dllm/blob/ca176752fbceec49c6b4777a2c18ae88e4eb10ed/examples/a2d/mdlm/sft.py#L41-L119), [encoder arguments and trainer, lines 41–119](https://github.com/ZHZisZZ/dllm/blob/ca176752fbceec49c6b4777a2c18ae88e4eb10ed/examples/bert/sft.py#L41-L119).
- Shared model defaults are dtype `bfloat16`, `load_in_4bit=False`, `lora=False`, adapter rank 32, alpha 64, dropout .05, target `all-linear`, no bias. Model loading tries `AutoModelForMaskedLM`, then `AutoModel`, passes dtype, attention implementation, device map and optional quantization configuration, then calls the optional adapter helper. [Model arguments, lines 11–24](https://github.com/ZHZisZZ/dllm/blob/ca176752fbceec49c6b4777a2c18ae88e4eb10ed/dllm/utils/configs.py#L11-L24), [loader, lines 28–79](https://github.com/ZHZisZZ/dllm/blob/ca176752fbceec49c6b4777a2c18ae88e4eb10ed/dllm/utils/models.py#L28-L79).
- Adapter configuration splits target module names and modules to save, creates `peft.LoraConfig`, then `get_peft_model`. With `lora=False`, this helper returns the model unchanged. Thus the nonquantized no-adapter path adds no parameter freezing here; exact trainable parameter counts still require inspecting the chosen instantiated model. [Adapter helper, lines 90–125](https://github.com/ZHZisZZ/dllm/blob/ca176752fbceec49c6b4777a2c18ae88e4eb10ed/dllm/utils/utils.py#L90-L125).
- Optional four-bit loading uses bitsandbytes NF4 with double quantization and the configured compute dtype, then calls `prepare_model_for_kbit_training(..., use_gradient_checkpointing=False)`. Merely specifying four-bit loading does not imply adapters are enabled. If bitsandbytes is unavailable this loader silently leaves quantization configuration unset. Do not describe the four-bit/no-adapter path as full parameter training. [Loader, lines 48–77](https://github.com/ZHZisZZ/dllm/blob/ca176752fbceec49c6b4777a2c18ae88e4eb10ed/dllm/utils/models.py#L48-L77).
- The repository pins Transformers 4.57.0, Accelerate 1.11.0, DeepSpeed .18.0 and PEFT .17.1; bitsandbytes .48.1 and Flash Attention 2.8.3 are optional dependencies. These are dependency declarations, not a verified working environment for the project. [Dependency declarations, lines 14–35](https://github.com/ZHZisZZ/dllm/blob/ca176752fbceec49c6b4777a2c18ae88e4eb10ed/pyproject.toml#L14-L35).

### Inferences
- A future full parameter recipe should explicitly set `lora=False` and `load_in_4bit=False`; an adapter recipe should explicitly set `lora=True`, target modules, rank, saved modules, and optional quantization. Record resolved configuration and actual trainable parameter count before comparing costs. The distinction follows the loading branches above, rather than assuming flags imply a successful runtime.
- Preserve Showdown serialization, conditioning fields, data split and stage identity while adapting records to `messages` or preprocessed token/label arrays. The upstream example datasets and learning rates do not validate the Pokémon task.

### Gaps
- No checkpoint was loaded, no model instantiated, and no installation or trainer execution occurred. Actual supported kernels, all-parameter trainability, adapter compatibility, memory fit and numerical behavior remain unverified.
- Reinforcement learning is excluded by the parent map. This note's one-forward statement covers the cited supervised trainers, not GRPO or the block trainer.

## What does the code prove about cost per example?

### Takeaway
Masking fewer targets does not shorten the dense transformer input. Both response and prompt positions run through the model. One corrupted full-sequence forward per microbatch is the source fact; wall time, dollars, and an advantage over block models remain unmeasured.

### Cited findings
- Each shared masked loss call samples one time per example, noises the full `[batch,length]` input tensor, calls `model` once with all positions, and computes cross entropy for all positions before multiplying by the masked-position indicator. There is no time-unrolled denoising loop, second clean teacher call, or slicing to only masked positions in this loss. [Loss body, lines 139–192](https://github.com/ZHZisZZ/dllm/blob/ca176752fbceec49c6b4777a2c18ae88e4eb10ed/dllm/core/trainers/mdlm.py#L139-L192).
- Evaluation `prediction_step` uses `torch.no_grad()` and calls the same stochastic loss once per evaluation batch. It does not sample full generated responses. [Prediction step, lines 102–116](https://github.com/ZHZisZZ/dllm/blob/ca176752fbceec49c6b4777a2c18ae88e4eb10ed/dllm/core/trainers/mdlm.py#L102-L116).
- Default supervised formatting retains the prompt in `input_ids`; prompt masking only sets corresponding labels to `-100`. The loss prevents corruption of labels `-100` but still sends those positions to the model. [Chat mapping, lines 225–253](https://github.com/ZHZisZZ/dllm/blob/ca176752fbceec49c6b4777a2c18ae88e4eb10ed/dllm/utils/data.py#L225-L253), [loss masking and call, lines 141–170](https://github.com/ZHZisZZ/dllm/blob/ca176752fbceec49c6b4777a2c18ae88e4eb10ed/dllm/core/trainers/mdlm.py#L141-L170).
- LLaDA, converted-model masked training and the encoder example request dynamic padding, deliberately pad labels with the tokenizer pad token rather than `-100`, and remove the attention mask. Consequently, batch padding is eligible for corruption/loss and is visible context in those recipes. [LLaDA collator, lines 110–119](https://github.com/ZHZisZZ/dllm/blob/ca176752fbceec49c6b4777a2c18ae88e4eb10ed/examples/llada/sft.py#L110-L119), [wrapper, lines 58–69](https://github.com/ZHZisZZ/dllm/blob/ca176752fbceec49c6b4777a2c18ae88e4eb10ed/dllm/utils/collators.py#L58-L69).
- The tokenizer uses right padding, and substitutes EOS for missing pad or vice versa. Do not universally call pad an EOS without examining the selected tokenizer. [Tokenizer, lines 118–131](https://github.com/ZHZisZZ/dllm/blob/ca176752fbceec49c6b4777a2c18ae88e4eb10ed/dllm/utils/models.py#L118-L131).
- Default max length is 1024 and truncation is `right`; implementation keeps the first `max_length` tokens, contrary to the argument help text's phrase “rightmost”. `filter` instead removes sequences exceeding the limit. Right truncation can cut the team answer. [Arguments, lines 32–47](https://github.com/ZHZisZZ/dllm/blob/ca176752fbceec49c6b4777a2c18ae88e4eb10ed/dllm/utils/configs.py#L32-L47), [actual clipping, lines 75–118](https://github.com/ZHZisZZ/dllm/blob/ca176752fbceec49c6b4777a2c18ae88e4eb10ed/dllm/utils/data.py#L75-L118).
- Dream's default per-batch cutoff chooses one batch response length and trims each longer response before padding. Its alternate probabilistic cutoff trims after padding. This is an objective/data alteration as well as a sequence-length change. [Collator, lines 44–128](https://github.com/ZHZisZZ/dllm/blob/ca176752fbceec49c6b4777a2c18ae88e4eb10ed/dllm/pipelines/dream/utils.py#L44-L128).
- Shared training defaults use train/eval batch four, gradient accumulation one, `bf16=True`, step evaluation and `eval_steps=0.1`, `save_steps=0.1`, and `save_only_model=True`. Floating .1 evaluation is a fraction of total steps, not a fixed every-0.1-step interval. [dllm arguments, lines 50–69](https://github.com/ZHZisZZ/dllm/blob/ca176752fbceec49c6b4777a2c18ae88e4eb10ed/dllm/utils/configs.py#L50-L69), [Transformers evaluation interval documentation, lines 1152–1158](https://github.com/huggingface/transformers/blob/76d27aea82449e921e36afdc886c6e5bf34ea526/src/transformers/training_args.py#L1152-L1158).
- In the declared Transformers 4.57.0 dependency, the training loop chunks microbatches by gradient accumulation, with a shorter final chunk; each microbatch calls `training_step`, which calls `compute_loss` and backward. On the ordinary path that means `A` full model forwards per optimizer update per device for accumulation `A`, fewer on the short final chunk. Checkpoint recomputation is additional internal work. [Loop, lines 2606–2624](https://github.com/huggingface/transformers/blob/76d27aea82449e921e36afdc886c6e5bf34ea526/src/transformers/trainer.py#L2606-L2624), [training-step call, lines 2663–2674](https://github.com/huggingface/transformers/blob/76d27aea82449e921e36afdc886c6e5bf34ea526/src/transformers/trainer.py#L2663-L2674), [loss and backward, lines 4014–4071](https://github.com/huggingface/transformers/blob/76d27aea82449e921e36afdc886c6e5bf34ea526/src/transformers/trainer.py#L4014-L4071).
- Gradient checkpointing is not an explicit dllm argument override; inherited Transformers defaults it off, and its trainer enables it when requested. The LLaDA hook changes the activation checkpoint strategy to whole-layer; the forward loop calls checkpointed blocks under that strategy. Dream explicitly branches to `_gradient_checkpointing_func` while training and disables use-cache there. [Inherited default, lines 1405–1415](https://github.com/huggingface/transformers/blob/76d27aea82449e921e36afdc886c6e5bf34ea526/src/transformers/training_args.py#L1405-L1415), [Trainer enable, lines 2445–2447](https://github.com/huggingface/transformers/blob/76d27aea82449e921e36afdc886c6e5bf34ea526/src/transformers/trainer.py#L2445-L2447), [LLaDA hook, lines 1052–1080](https://github.com/ZHZisZZ/dllm/blob/ca176752fbceec49c6b4777a2c18ae88e4eb10ed/dllm/pipelines/llada/models/modeling_llada.py#L1052-L1080), [LLaDA blocks, lines 1355–1384](https://github.com/ZHZisZZ/dllm/blob/ca176752fbceec49c6b4777a2c18ae88e4eb10ed/dllm/pipelines/llada/models/modeling_llada.py#L1355-L1384), [Dream blocks, lines 657–713](https://github.com/ZHZisZZ/dllm/blob/ca176752fbceec49c6b4777a2c18ae88e4eb10ed/dllm/pipelines/dream/models/modeling_dream.py#L657-L713).
- Dream's CART computation allocates a `[length,length]` geometric matrix in addition to transformer work. It is not an additional transformer pass. [CART, lines 23–36](https://github.com/ZHZisZZ/dllm/blob/ca176752fbceec49c6b4777a2c18ae88e4eb10ed/dllm/pipelines/dream/trainer.py#L23-L36).

### Inferences
- Planning arithmetic only: for `N` example visits, per-device microbatch `B`, accumulation `A`, and data parallel device count `D`, optimizer updates are approximately `ceil(N/(B*A*D))`, with epoch/end-batch caveats. Total ordinary training forwards across devices are approximately `N/B`, not `N/(B*A*D)`. A claimed “one pass per step” must name microbatch or optimizer step. This follows the cited loss and dependency loop.
- A hardware estimate must measure seconds per example with actual prompt+team token length and padding. Holding a long prompt fixed saves corruption/scoring targets, not transformer positions. Dense attention's interaction term grows with sequence length squared, while other model operations scale roughly with length; this is structural reasoning, not a runtime ratio or price.
- Increasing microbatch size may improve hardware use but also changes padding and activation memory. Increasing accumulation changes update batch size while retaining separate microbatch forward/backward work. Neither predicts a dollar saving by itself.
- Activation checkpointing trades recomputation for memory; low precision and adapters alter memory/optimizer work. None proves a wall-time or dollar benefit in this task. Model load dtype, mixed precision, quantized storage, and loss dtype are separate settings. Log all four.
- A future cost estimate should use GPU-seconds actually measured for training, held-out loss passes, probes, setup, checkpoint writing and retries, multiplied by the then-approved Modal rate, divided by a declared denominator such as unique examples or example visits. Do not insert numbers from block model measurements. No dollar estimate is established here.

### Gaps
- No throughput, peak memory, numerical stability, accuracy, quality per dollar, or masked-vs-block speed ratio was measured.
- No model-specific effective attention kernel or device capability was verified. `attn_implementation` is a loader option, not evidence a chosen backend works.
- Exact LoRA trainable parameters and savings depend on selected model modules and PEFT behavior; neither was instantiated. LoRA does not imply only adapter tokens run through the transformer.
- Exact gradient-accumulation normalization for every wrapped model remains unverified. `MDLMTrainer.compute_loss` accepts but ignores `num_items_in_batch`; do not assume it produces a single global token-weighted loss across unequal-length microbatches solely because it subclasses Trainer. Its per-call normalization is explicit in [lines 200–209](https://github.com/ZHZisZZ/dllm/blob/ca176752fbceec49c6b4777a2c18ae88e4eb10ed/dllm/core/trainers/mdlm.py#L200-L209).
