# RIBS framework and pyribs components

## Concepts, framework, and version

### Takeaway
RIBS separates candidate generation, storage and feedback routing. The user supplies evaluations between ask and tell. [Paper, Figure 1 and section 3](https://arxiv.org/html/2303.00191)

### Cited Findings
- Quality diversity optimization seeks many high-performing solutions with different measured properties. The paper defines a scalar objective f and a vector of measure functions m; the ideal is to maximize f at every attainable measure vector, relaxed to a finite representative archive. Measures were previously called behavior characteristics, behavior descriptors or feature descriptors. [Paper, section 2.1](https://arxiv.org/html/2303.00191)
- Thus illumination means discovering representative high-quality solutions throughout measure space, rather than returning only a single global optimum. In the paper's heatmaps, coordinates are measures and color is objective value. [Paper, sections 2.1 and 4.2.7](https://arxiv.org/html/2303.00191)
- RIBS expands to Rapid Illumination of Behavior Space. Its name comes from Fontaine et al.'s paper title, “Covariance Matrix Adaptation for the Rapid Illumination of Behavior Space”; pyribs combines Python with RIBS. The conceptual framework has an archive, one or more emitters, and a scheduler; pyribs implements it. [Paper, introduction footnote 1 and section 3](https://arxiv.org/html/2303.00191)
- As checked November 11, 2026, latest stable is 0.12.1. PyPI wheel upload is November 7, 2026 at 09:41:29 UTC; GitHub release publication is November 7 at 09:34:13 UTC. Cached search results showing 0.12.0 are stale. [PyPI live JSON](https://pypi.org/pypi/ribs/json), [GitHub live release metadata](https://api.github.com/repos/icaros-usc/pyribs/releases/latest), [release](https://github.com/icaros-usc/pyribs/releases/tag/v0.12.1)

### Inferences
- For an explainer, draw solution space separately from measure space: mutation changes solution parameters; evaluation determines the archive location. This follows the paper's mappings f and m. [Paper, section 2.1](https://arxiv.org/html/2303.00191)

### Gaps
- Direct stable-doc fetching returned HTTP 403 in this research environment. Current contracts below are checked against official v0.12.1 source, including the docstrings that generate the API documentation. [Tagged source](https://github.com/icaros-usc/pyribs/tree/v0.12.1)

## Archive and emitter contracts

### Takeaway
Archives organize evaluated candidates and produce insertion feedback. Emitters generate candidates and may adapt to that feedback. [Archive module](https://github.com/icaros-usc/pyribs/blob/v0.12.1/ribs/archives/__init__.py), [emitter module](https://github.com/icaros-usc/pyribs/blob/v0.12.1/ribs/emitters/__init__.py)

### Cited Findings
- Archive definition: “a data structure that stores solutions generated by the QD algorithm,” together with objective, measures and other relevant information. [Archive module](https://github.com/icaros-usc/pyribs/blob/v0.12.1/ribs/archives/__init__.py)
- `GridArchive.add(solution, objective, measures, **fields)` accepts aligned batches, conventionally solution shape B×D, objective B, measures B×K. It inserts candidates whose objective exceeds their cell threshold. Among candidates for one cell, highest objective wins; first occurrence breaks ties. Defaults recover best-per-cell MAP-Elites; soft thresholds support annealing. [GridArchive source and add docstring](https://github.com/icaros-usc/pyribs/blob/v0.12.1/ribs/archives/_grid_archive.py)
- Return is an `add_info` dictionary, not a universal two-element tuple. For GridArchive its arrays include `status` and `value`. Status 0 means not added, 1 improvement of an existing cell, 2 discovery of a new cell. Feedback compares against the archive before the batch: two competing candidates can both have status 2 although only one survives. [GridArchive.add](https://github.com/icaros-usc/pyribs/blob/v0.12.1/ribs/archives/_grid_archive.py)
- With default thresholds, `value` is objective minus incumbent objective for occupied cells, and the candidate objective for new cells. A rejected tie can have zero improvement. Other threshold settings use objective minus threshold. Do not equate value with objective in all cases or interpret status as a final survival flag. [GridArchive.add](https://github.com/icaros-usc/pyribs/blob/v0.12.1/ribs/archives/_grid_archive.py)

| CVTArchive | Nearest-centroid Voronoi region; a fixed number of centroids partitions measure space, normally generated with k-means. | [source](https://github.com/icaros-usc/pyribs/blob/v0.12.1/ribs/archives/_cvt_archive.py) |
| SlidingBoundariesArchive | Grid whose boundaries periodically remap using a buffer of recent solutions; starts with uniform intervals. | [source](https://github.com/icaros-usc/pyribs/blob/v0.12.1/ribs/archives/_sliding_boundaries_archive.py) |
| CategoricalArchive | Cartesian combinations of named categories, one categorical variable per measure dimension. | [source](https://github.com/icaros-usc/pyribs/blob/v0.12.1/ribs/archives/_categorical_archive.py) |
| ProximityArchive | Unstructured collection, no predefined grid cells; admission uses nearest-neighbor novelty and a novelty threshold, optionally local competition. Returns novelty feedback. | [source](https://github.com/icaros-usc/pyribs/blob/v0.12.1/ribs/archives/_proximity_archive.py) |
| DensityArchive | No elites or spatial cells; reservoir-sampled measure buffer supports density estimation. A separate result archive stores solutions. | [source](https://github.com/icaros-usc/pyribs/blob/v0.12.1/ribs/archives/_density_archive.py) |
| DiscountArchive | A learned smooth discount function replaces the histogram of per-cell discounts; supplies model training data and improvement feedback. User explicitly initializes and trains the model. | [source](https://github.com/icaros-usc/pyribs/blob/v0.12.1/ribs/archives/_discount_archive.py) |
| DNSArchive | Fixed-size population, not spatial bins; merges candidates and retains survivors using distance to fitter neighbors, the Dominated Novelty Search score. | [source](https://github.com/icaros-usc/pyribs/blob/v0.12.1/ribs/archives/_dns_archive.py) |
| ArchiveBase | Shared abstract archive interface, not another tessellation. | [source](https://github.com/icaros-usc/pyribs/blob/v0.12.1/ribs/archives/_archive_base.py) |

- Emitter definition: “algorithms that generate solutions and adapt to objective, measure, and archive insertion feedback.” [Emitter module](https://github.com/icaros-usc/pyribs/blob/v0.12.1/ribs/emitters/__init__.py)
- `ask()` takes no evaluation arguments and returns a batch of candidate solutions. `tell(solution, objective, measures, add_info, **fields)` accepts those evaluated candidates and their archive feedback, and returns None. Stateless emitters can leave tell as a no-op. A custom emitter subclasses `EmitterBase`, overriding generation and, when needed, adaptation. [EmitterBase](https://github.com/icaros-usc/pyribs/blob/v0.12.1/ribs/emitters/_emitter_base.py)

| Emitter | How it generates candidates | Source |
| --- | --- | --- |
| GaussianEmitter | Samples archived parents and applies Gaussian perturbation; uses initial solutions or x0 when archive is empty. | [source](https://github.com/icaros-usc/pyribs/blob/v0.12.1/ribs/emitters/_gaussian_emitter.py) |
| IsoLineEmitter | Adds isotropic Gaussian noise and a random displacement along the line between two sampled elites. | [source](https://github.com/icaros-usc/pyribs/blob/v0.12.1/ribs/emitters/_iso_line_emitter.py) |
| EvolutionStrategyEmitter | Maintains an evolution strategy, default CMA-ES, sampling and adapting its distribution according to ranking, selection and restart configuration. | [source](https://github.com/icaros-usc/pyribs/blob/v0.12.1/ribs/emitters/_evolution_strategy_emitter.py) |
| GradientArborescenceEmitter | Samples coefficients for objective and measure gradients to branch from a solution point; adapts coefficient search and moves the solution point. | [source](https://github.com/icaros-usc/pyribs/blob/v0.12.1/ribs/emitters/_gradient_arborescence_emitter.py) |
| GradientOperatorEmitter | Uses objective and measure gradients as variation operators for differentiable quality diversity. | [source](https://github.com/icaros-usc/pyribs/blob/v0.12.1/ribs/emitters/_gradient_operator_emitter.py) |
| GeneticAlgorithmEmitter | Applies a configurable genetic operator to parents; supports initial solutions or applying its operator to x0 when empty. | [source](https://github.com/icaros-usc/pyribs/blob/v0.12.1/ribs/emitters/_genetic_algorithm_emitter.py) |
| BayesianOptimizationEmitter | Uses Bayesian optimization for BOP-Elites; pairs with its specialized scheduler. | [source](https://github.com/icaros-usc/pyribs/blob/v0.12.1/ribs/emitters/_bayesian_opt_emitter.py) |

- Rankers determine candidate ordering used by adaptive emitters. `rank(emitter, archive, data, add_info)` returns ordering indices and ranking values; reset can refresh internal state. Options include objective, improvement, random measure direction, novelty, density and local-competition ranking. Two-stage improvement ranks insertion status first, improvement second; single-stage improvement is explicitly discouraged for CMA-ME because new-cell and occupied-cell improvement values have different scales. [Rankers source](https://github.com/icaros-usc/pyribs/blob/v0.12.1/ribs/emitters/rankers.py)

### Inferences
- A universal picture of an archive as a rectangular heatmap would misrepresent proximity, density, discount and population archives. Use the table's geometry instead. [Archive exports](https://github.com/icaros-usc/pyribs/blob/v0.12.1/ribs/archives/__init__.py)

### Gaps
- A single universal meaning for every archive's `add_info` fields is not found; inspect the concrete class. The GridArchive status/value contract above must not be generalized to DensityArchive. [ArchiveBase](https://github.com/icaros-usc/pyribs/blob/v0.12.1/ribs/archives/_archive_base.py)

## Scheduler, user workflow, and algorithm recipes

### Takeaway
The scheduler owns the routing loop, while user code owns evaluation. Component class names alone do not fully specify an algorithm; threshold, ranker, restart and optimizer configuration matter. [Scheduler](https://github.com/icaros-usc/pyribs/blob/v0.12.1/ribs/schedulers/_scheduler.py), [supported algorithms](https://docs.pyribs.org/en/stable/supported-algorithms.html)

### Cited Findings
- Scheduler definition: “A basic class that composes an archive with multiple emitters.” Construct it with an archive and distinct emitter instances. [Scheduler source](https://github.com/icaros-usc/pyribs/blob/v0.12.1/ribs/schedulers/_scheduler.py)
- `Scheduler.ask()` calls every emitter's ask, remembers batch lengths and concatenates solutions along axis 0. User evaluates those solutions. `tell(objective, measures, **fields)` validates lengths, adds the remembered solutions to the archive, optionally also a result archive, then slices solutions, evaluations and add_info by emitter and calls each emitter's tell. It returns None. Order must match ask; repeated ask without tell raises an error. Batch insertion is default, with optional sequential `add_single` mode. [Scheduler implementation](https://github.com/icaros-usc/pyribs/blob/v0.12.1/ribs/schedulers/_scheduler.py)
- `BanditScheduler` uses Upper Confidence Bound 1 to choose `num_active` emitters from a pool, with configurable reselection and insertion-success feedback. Ordinary Scheduler asks all emitters. BanditScheduler does not support differentiable quality diversity emitters. [BanditScheduler](https://github.com/icaros-usc/pyribs/blob/v0.12.1/ribs/schedulers/_bandit_scheduler.py)
- A third public scheduler, `BayesianOptimizationScheduler`, supports archive upscaling and is specifically paired with BayesianOptimizationEmitter and GridArchive. [API](https://docs.pyribs.org/en/stable/api/ribs.schedulers.BayesianOptimizationScheduler.html)
- The paper explicitly assigns managing archive/emitter interaction to the scheduler and explains multi-emitter search as exploring multiple regions while balancing exploration. It leaves evaluations to user code because evaluation dependencies and hardware differ across applications. The basic scheduler is routing; the bandit scheduler also allocates effort. [Paper, sections 2.1.3, 3.1.3 and 4.2.4](https://arxiv.org/html/2303.00191)
- Typical user code constructs archive, emitters and scheduler once, then repeats `solutions = scheduler.ask(); objective, measures = evaluate(solutions); scheduler.tell(objective, measures)`. Evaluation can run outside pyribs and in parallel. [Official README](https://github.com/icaros-usc/pyribs/blob/v0.12.1/README.md), [paper](https://arxiv.org/html/2303.00191)
- Differentiable workflows also call `ask_dqd()` and `tell_dqd(objective, measures, jacobian)`, with Jacobian shape B×(1+K)×D, objective gradient followed by measure gradients, before the branching ask/tell phase. Thus “loop calls only ask and tell” applies to the ordinary workflow. [Scheduler source](https://github.com/icaros-usc/pyribs/blob/v0.12.1/ribs/schedulers/_scheduler.py)
- Users read archive `data()`, `stats`, and `sample_elites(n)`; visualizations consume archive data, e.g. grid/CVT/sliding-boundary heatmaps and parallel axes plots. Sampling also supplies parents to emitters. [ArchiveBase](https://github.com/icaros-usc/pyribs/blob/v0.12.1/ribs/archives/_archive_base.py), [visualize module](https://github.com/icaros-usc/pyribs/blob/v0.12.1/ribs/visualize/__init__.py)
- Direct archive.add is useful when implementing custom control flow or importing already evaluated solutions. The paper explicitly shows direct insertion of true evaluations into a ground-truth archive in surrogate-assisted optimization. Custom candidate-generation/adaptation logic belongs in an EmitterBase subclass. [Paper, Algorithm 2](https://arxiv.org/html/2303.00191), [EmitterBase](https://github.com/icaros-usc/pyribs/blob/v0.12.1/ribs/emitters/_emitter_base.py)

### Inferences
- Without Scheduler, an equivalent ordinary batch loop must ask each emitter, retain its batch length, concatenate, evaluate, call archive.add, then tell each emitter its corresponding solutions/evaluations/add_info slice. This is an implementation-derived reconstruction, not a quotation or an assertion that the docs teach a scheduler-free recipe. [Scheduler source](https://github.com/icaros-usc/pyribs/blob/v0.12.1/ribs/schedulers/_scheduler.py)
- Suggested visual flow: user → scheduler.ask → emitters → candidate batch → user evaluation → scheduler.tell → archive.add → insertion feedback → emitter.tell. The archive also supplies sampled elites to relevant emitters. [Paper Figure 1](https://arxiv.org/html/2303.00191), [GaussianEmitter](https://github.com/icaros-usc/pyribs/blob/v0.12.1/ribs/emitters/_gaussian_emitter.py)

### Gaps
- An explicit docs quotation saying the scheduler exists specifically to avoid writing concatenate-and-slice boilerplate was not found. That rationale is an inference from the code; management of interaction and allocation across emitters are explicitly stated in the paper. [Paper](https://arxiv.org/html/2303.00191)
