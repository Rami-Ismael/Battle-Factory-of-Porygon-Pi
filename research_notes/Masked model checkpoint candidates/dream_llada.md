# Dream and LLaDA checkpoint evidence

## What are the resolved checkpoints and architecture facts?

### Takeaway
Dream resolves to `Dream-org/Dream-v0-Base-7B`; LLaDA resolves to `GSAI-ML/LLaDA-8B-Base`. I also inspected LLaDA Instruct to disambiguate that family. These are genuine full bidirectional mask predictors, without a block attention pattern in the inspected default forward paths. A block-by-block unmasking schedule is distinct from block attention.

### Cited Findings
Use these immutable revisions throughout. File links below are evidence, not model-card descriptions.

- Dream revision `6572adb5535263e4d1a337b56942ba48b6dee2a9` has 28 layers, width 3584, 28 query heads, four key/value heads, vocabulary 152064, no sliding window, `max_position_embeddings=131072`, BF16 configuration, untied embeddings, and custom `AutoConfig`/`AutoModel` mappings. [config](https://huggingface.co/Dream-org/Dream-v0-Base-7B/blob/6572adb5535263e4d1a337b56942ba48b6dee2a9/config.json)
- Dream attention explicitly sets `is_causal=False` in SDPA and sends no attention mask for the sampler's `"full"` sentinel. No block mask is constructed. `generation_utils.py` lines 388–412 pads the prompt with masks and calls `self(x, attention_mask, tok_idx)` for every step, including prompt tokens. The forward creates full-sequence logits and the sampler then creates a shifted full-sequence logits tensor with `torch.cat`. [model code](https://huggingface.co/Dream-org/Dream-v0-Base-7B/blob/6572adb5535263e4d1a337b56942ba48b6dee2a9/modeling_dream.py#L424), [sampler](https://huggingface.co/Dream-org/Dream-v0-Base-7B/blob/6572adb5535263e4d1a337b56942ba48b6dee2a9/generation_utils.py#L388)
- LLaDA Base revision `0f2787f2d87eac5eed8a087d5ecd24277e6255b2` has 32 layers, width 4096, 32 query and key/value heads, vocabulary 126464, `max_sequence_length=4096`, BF16 configuration, untied embeddings, `flash_attention=false`, `alibi=false`, `use_cache=false`, and custom configuration/model mappings. `block_type=llama` describes its transformer module, not an attention block mask. [config](https://huggingface.co/GSAI-ML/LLaDA-8B-Base/blob/0f2787f2d87eac5eed8a087d5ecd24277e6255b2/config.json)
- LLaDA uses SDPA with `is_causal=False`, and any padding bias is combined with bidirectional rather than causal bias when ALiBi is disabled. Its forward asserts `past_key_values is None and not use_cache` with message `The kvcache is not suppotred for MDM.` [attention](https://huggingface.co/GSAI-ML/LLaDA-8B-Base/blob/0f2787f2d87eac5eed8a087d5ecd24277e6255b2/modeling_llada.py#L628), [forward](https://huggingface.co/GSAI-ML/LLaDA-8B-Base/blob/0f2787f2d87eac5eed8a087d5ecd24277e6255b2/modeling_llada.py#L1218)
- LLaDA Instruct revision `08b83a6feb34df1a6011b80c3c00c7563e963b07` has the same configuration, parameter dimensions, byte size and dtype; its tokenizer has extra chat tokens but the same mask token. [config](https://huggingface.co/GSAI-ML/LLaDA-8B-Instruct/blob/08b83a6feb34df1a6011b80c3c00c7563e963b07/config.json), [tokenizer](https://huggingface.co/GSAI-ML/LLaDA-8B-Instruct/blob/08b83a6feb34df1a6011b80c3c00c7563e963b07/tokenizer_config.json)
- Official LLaDA sampler revision `9182493720ed723ef8031210d85959364e51cbe0` constructs `x` as prompt plus full generation region and calls `model(x)` every step. `block_length` restricts which positions can be committed, not model attention. Guidance concatenates conditional and unconditional rows and doubles batch memory. Nonzero temperature explicitly promotes logits and random noise to float64. [sampler](https://github.com/ML-GSAI/LLaDA/blob/9182493720ed723ef8031210d85959364e51cbe0/generate.py#L96)

### Inferences
- Both models recompute the prompt at every step. Prompt hidden states depend on changing generated tokens, so ordinary exact autoregressive prefix key/value caching is invalid across steps. Dream contains cache plumbing and config `use_cache=true`, but its sampler does not reuse returned key/value states between calls. Embedding lookups, static rotary frequencies and static mask structures can be reused; that does not remove transformer computation on prompt tokens. Approximate diffusion caching would change the implementation and needs separate accuracy validation.
- Closest existing project block baseline for Dream is the Qwen2.5 3B block fine-tune by family, not size: Dream has Qwen-like grouped-query attention and tokenizer machinery. Fast-dLLM v2 1.5B is also a Qwen-family baseline. The inspected files do not prove a pretrained lineage or a same-size block checkpoint suitable for a controlled swap. LLaDA has no clean architecture-and-tokenizer matched counterpart among those project block baselines. Do not call LLaDA a converted LLaMA checkpoint merely because `block_type` says llama.

### Gaps
- No same-size block sibling checkpoint was verified for either family. The swap test is not architecture controlled against the named 1.5B/3B baselines.
- No generation or Apple-silicon test was performed. The configs prove configured positions, not long-context quality or trained context coverage.

## What do the weight files, tokenizer files, and memory arithmetic establish?

### Takeaway
Dream's released BF16 sampler is ruled out for a 24,644-token prompt on this 24 GB laptop by its full logits and shifted-logits allocations alone. LLaDA is ruled out for this prompt by its configured 4096-position limit. Neither should be called universally unable to run on 24 GB with a short prompt and a changed sampler.

### Cited Findings
All counts below sum tensor shapes from safetensors headers obtained with two HTTP range requests per shard, first eight bytes then exactly the header. No tensor data was downloaded. Each response is retained in its own new directory in `dream_llada/`, with `source.txt` holding its immutable URL. API snapshots list full shard file sizes. The locally authored `inspect_files.py` was run with `python3 -I`; downloaded Python was only read as text.

- Dream tokenizer is custom `DreamTokenizer`, byte-level byte-pair encoding using `vocab.json` and `merges.txt`. Mask is `<|mask|>` ID 151666, with tokenizer and model limit 131072. A 24,644-token input fits the configured range with room for output, if that count is in Dream tokens. [tokenizer config](https://huggingface.co/Dream-org/Dream-v0-Base-7B/blob/6572adb5535263e4d1a337b56942ba48b6dee2a9/tokenizer_config.json), [mask ID](https://huggingface.co/Dream-org/Dream-v0-Base-7B/blob/6572adb5535263e4d1a337b56942ba48b6dee2a9/added_tokens.json), [tokenizer implementation](https://huggingface.co/Dream-org/Dream-v0-Base-7B/blob/6572adb5535263e4d1a337b56942ba48b6dee2a9/tokenization_dream.py)
- LLaDA is `PreTrainedTokenizerFast`, tokenizer JSON BPE with NFC normalization. Mask is `<|mdm_mask|>` ID 126336. Tokenizer `model_max_length` is an effectively infinite sentinel; it does not override model `max_sequence_length=4096`. Thus a 24,644-token prompt is outside its configured limit. ### Inferences
These are arithmetic estimates, not measured peaks. Batch one, no guidance, BF16 resident weights and activations, total sequence length S including output; GiB means 2^30 bytes. They omit allocator reserve, operating system, battles, loading duplication, activations, sampling workspaces and cache overhead unless specified.

- Dream weights alone are 14.185 GiB. BF16 full logits are `2*S*152064` bytes. At S=24,644 this is 6.980 GiB. The sampler's `torch.cat` constructs another full logits tensor while its input logits remain live: weights plus those two tensors alone are about 28.146 GiB, already beyond 24 GB. Output tokens increase this. Therefore released BF16 Dream plus unchanged sampler at this prompt is ruled out even with memory-efficient attention; this is stronger than an unmeasured generic fit assertion. Altering the sampler to compute only masked output logits and avoid full shifting could change this verdict.
- Dream eager attention materializes a `[1,28,S,S]` score tensor: 31.675 GiB in BF16 or 63.349 GiB in FP32 at S=24,644, before other tensors. SDPA need not materialize it, so this is a backend-dependent allocation estimate, not a claim that every Dream implementation uses this memory.
- LLaDA weights alone are 14.930 GiB. At S=4096 full BF16 logits are 0.965 GiB; weights plus logits are 15.895 GiB before sampler and activations. One materialized `[1,32,S,S]` attention matrix is 1 GiB BF16 or 2 GiB FP32. Short-context coexistence with battles is unverified and depends on their resident memory and SDPA backend. Nonzero-temperature float64 sampling increases memory and needs changes for MPS.
- For comparison only, extending LLaDA to S=24,644 would have 5.805 GiB BF16 logits and 36.199/72.399 GiB BF16/FP32 attention matrices; the extension is not validated and is outside config. These numbers do not confer long-context support.

### Gaps
- Actual tokenizer counts of the Jev prompt were not measured; the 24,644 count cannot be transferred between tokenizers without counting its exact text.
- No peak working set, loading peak, Apple kernel dispatch, quantized checkpoint, battle memory budget or speed was measured. No universal short-context 24 GB rejection is justified from these files alone.

## What code and licensing must a public fine tune carry?

### Takeaway
Both need custom model code under the released Transformers interfaces, but their forward paths provide PyTorch SDPA rather than requiring CUDA-only FlashAttention. That is evidence for a possible MPS port, not proof of a working laptop implementation. Dream's code has an actual Apache-2.0 license; LLaDA's model license is declared MIT but the inspected model and upstream repository lack a standalone model MIT license text.

### Cited Findings
- Dream custom modeling imports optional FlashAttention only behind availability checks, and exposes SDPA plus eager attention. Model and tokenizer Python headers state Apache-2.0. A complete Apache-2.0 license is present in Dream upstream revision `31f94a60d187e3fd481fee3bbc2c732eb94a879c`. [model code](https://huggingface.co/Dream-org/Dream-v0-Base-7B/blob/6572adb5535263e4d1a337b56942ba48b6dee2a9/modeling_dream.py), [upstream license](https://github.com/DreamLM/Dream/blob/31f94a60d187e3fd481fee3bbc2c732eb94a879c/LICENSE)
- Dream weight license itself is declared `apache-2.0` in the pinned model repository's metadata. This is license evidence only, not architectural evidence. No standalone model license file is in its checkpoint repository. [declaration](https://huggingface.co/Dream-org/Dream-v0-Base-7B/blob/6572adb5535263e4d1a337b56942ba48b6dee2a9/README.md)
- LLaDA config disables flash attention; code's fallback is PyTorch SDPA. It still contains CUDA backend toggles and a CUDA-or-CPU auto-device helper. The sample script chooses `device='cuda'`. Code must be reviewed/adapted to explicit `mps`; do not claim turnkey Apple compatibility. [model](https://huggingface.co/GSAI-ML/LLaDA-8B-Base/blob/0f2787f2d87eac5eed8a087d5ecd24277e6255b2/modeling_llada.py), [sampler](https://github.com/ML-GSAI/LLaDA/blob/9182493720ed723ef8031210d85959364e51cbe0/generate.py)
- LLaDA pinned checkpoint metadata declares MIT. Upstream README at `9182493720ed723ef8031210d85959364e51cbe0` also explicitly declares Base and Instruct MIT. Its tree has no project/model MIT LICENSE file, only a third-party `opencompass/LICENSE`. [checkpoint declaration](https://huggingface.co/GSAI-ML/LLaDA-8B-Base/blob/0f2787f2d87eac5eed8a087d5ecd24277e6255b2/README.md), [upstream declaration](https://github.com/ML-GSAI/LLaDA/blob/9182493720ed723ef8031210d85959364e51cbe0/README.md#license)

### Inferences
- Apache redistribution requires a copy of Apache-2.0, preservation of applicable copyright/attribution notices, notices of changed files, and any applicable upstream NOTICE contents. A public Dream fine-tune should identify its pinned base and changes and retain its custom code notices. The full license text cited above specifies these conditions.
- MIT redistribution ordinarily requires the copyright and permission notice with substantial portions. For LLaDA, preserve the pinned MIT declarations and obtain/clarify the actual applicable copyright and permission text before publishing a derivative; the inspected sources do not supply a complete model license notice. Do not invent its copyright holder or treat a third-party license as the model license.
- Ordinary float64 MPS limitations make LLaDA's nonzero-temperature sampler a porting concern; use a supported dtype only after checking sampling effects. This is not a benchmark or an executed compatibility result.

### Gaps
- LLaDA full model MIT license notice was not verified. Dream weight license is a repository declaration with corroborating code license, not a license stored in tensor headers.
- No tested Apple-silicon runtime or exact runtime dependency lock was established. BF16 availability and CUDA-backend toggle behavior depend on installed PyTorch/macOS versions. Do not describe either stock repository as verified to run on M4 Pro.

### Local validation finding
- The retained, unmodified LLaDA Base `special_tokens_map.json` response is malformed JSON: the `<|mdm_mask|>` entry lacks a comma before `<role>` on lines 3–4. Its `source.txt` records the pinned download URL. This is the remote file content captured during inspection, not an edit introduced locally. [pinned malformed file](https://huggingface.co/GSAI-ML/LLaDA-8B-Base/blob/0f2787f2d87eac5eed8a087d5ecd24277e6255b2/special_tokens_map.json)
- The separately retained Base `tokenizer.json` and `tokenizer_config.json` are valid JSON and independently establish BPE tokenization and `<|mdm_mask|>` ID 126336. The Instruct special-token map is valid. Thus the mask-ID finding survives, but a standard Base tokenizer loader that parses the malformed map can fail before tokenization. [Base tokenizer config](https://huggingface.co/GSAI-ML/LLaDA-8B-Base/blob/0f2787f2d87eac5eed8a087d5ecd24277e6255b2/tokenizer_config.json), [Base tokenizer](https://huggingface.co/GSAI-ML/LLaDA-8B-Base/blob/0f2787f2d87eac5eed8a087d5ecd24277e6255b2/tokenizer.json), [Instruct map](https://huggingface.co/GSAI-ML/LLaDA-8B-Instruct/blob/08b83a6feb34df1a6011b80c3c00c7563e963b07/special_tokens_map.json)
- Inference, not an executed fix: a documented local tokenizer copy with that comma repaired, or a loader explicitly built from the valid tokenizer JSON plus special-token declarations, could avoid this parsing failure. No fallback was run and end-to-end tokenizer loading remains unverified. Preserve the original evidence file unchanged and record any future repair as a modification.
