The pyribs loop,
one turn at a time

pyribs is a Python library for quality diversity optimization. It implements RIBS, short for Rapid Illumination of Behavior Space: an archive, one or more emitters and a scheduler. Your code sits between their ask and their tell. Step the machine below to watch one batch go round.

THE MACHINE
Four lanes, one batch

Each lane is one level of abstraction. Your code is on top. Below it the scheduler routes, the emitters propose candidates, and the archive stores what it keeps.

The archive is the data structure that stores the solutions the algorithm generates, together with each one's objective, measures and other fields.

An emitter is one of the "algorithms that generate solutions and adapt to objective, measure, and archive insertion feedback." Its ask() returns a batch. Its tell() takes that batch back with its scores and the archive's verdict.

The scheduler is "a basic class that composes an archive with multiple emitters." It calls every emitter, joins their batches, hands them to you, and after you score them it adds them to the archive and returns each emitter its own slice.

QUESTION 1
What Rapid Illumination of Behavior Space means

RIBS is the conceptual framework of archive, emitters and scheduler. pyribs is Python plus RIBS.

The name comes from a paper title by Fontaine and colleagues, "Covariance Matrix Adaptation for the Rapid Illumination of Behavior Space."

A quality diversity problem has one scalar objective f and a vector of measure functions m. The ideal is the best objective at every reachable measure vector, relaxed to a finite archive of representatives.

Illumination means finding representative high-quality solutions throughout measure space instead of one global optimum. "Behavior space" is measure space under its older name: measures were once called behavior characteristics or behavior descriptors.

The paper's heatmaps draw it this way: coordinates are measures, colour is objective.

QUESTION 3
Where your code meets each part

You build all three once. In the loop you call only the scheduler. You reach the emitter lane by subclassing, and the archive lane by reading results.

The ordinary loop is three lines: scheduler.ask(), your evaluation, scheduler.tell(objective, measures). Evaluation runs outside pyribs and can run in parallel.

Two exceptions. Differentiable workflows first call ask_dqd() and tell_dqd(objective, measures, jacobian). Custom control flow, or importing solutions you already scored, calls archive.add directly.

QUESTION 4
Why a scheduler

With several emitters, someone must remember which rows came from whom, add the joined batch to the archive once, and hand each emitter only its slice. The scheduler does that bookkeeping.

Turn the Scheduler switch off in the machine above. Its lane disappears and the ledger of batch lengths moves into your code. The code panel shows the loop you would then write.

The paper gives two reasons for the design. The scheduler manages how archive and emitters interact, and several emitters can explore several regions at once. Evaluation stays in your code because dependencies and hardware differ across applications.

The docs never say the scheduler exists to save you the slicing code. That reason is read from the Scheduler source, and the loop on the right is a reconstruction from it, not a recipe from the docs.

QUESTION 5
Novelty search: the archive lane, swapped

Replace the grid with a ProximityArchive. It has no cells. It admits a candidate when it is far enough from what is already stored.

A candidate's novelty is its mean Euclidean distance to its nearest archived neighbours. pyribs measures against the current archive only; candidates in the same batch are not each other's neighbours. Admission is novelty >= novelty_threshold, so equality passes.

Three modes change one rule each. Plain novelty search ignores the objective. Local competition lets a candidate that is not novel replace its single closest neighbour if it is strictly better. Threshold decay lowers the cutoff after add calls that admit nothing. The novelty formula never changes.

The emitter side changes its ranker: ranker="nov" sorts by novelty, ranker="nslc" runs a Pareto sort on novelty and local competition. Threshold decay changes only the archive.

The Maze loadout in the machine runs the plain mode with the tutorial's settings.

ρ(x) = (1/k) · Σi=1..k dist(x, μi) k = min(k_neighbors, archive size)

Decay is off by default, threshold_decay_rate=None. The rate must lie in the interval from 0, exclusive, to 1. After threshold_decay_itrs consecutive add calls with no novel addition the threshold becomes max(threshold_decay_min, threshold * rate). Replacements alone do not reset the counter. The docs' supported-algorithms page lists novelty search and Novelty Search with Local Competition but has no entry named threshold decay. History: ProximityArchive and local competition arrived in v0.8.0, NSLCRanker in v0.11.0, threshold decay in v0.12.0.

Orchestrating LLMs to Write Diverse Stories with Quality Diversity through AI Feedback

A solution is a Python string: a story about a suspicious spy and a rich politician. A language model, Llama 3.1 8B instruct at q4_K_M, both rewrites stories and rates them.

The objective asks whether it is a high-quality short story about those two characters. Measure 0 asks whether it is a romance, measure 1 whether it has a happy ending. Each rating is clipped to 1 to 10 and averaged over five calls, so one story costs 15 rating calls.

The custom emitter samples an elite, picks up or down for each measure, and asks the model to rewrite. It defines no tell, so the inherited one adapts nothing.

Incorporating Human Feedback into Quality Diversity for Diversified Text-to-Image Generation

A solution is a Stable Diffusion starting latent, 4 by 32 by 32, flattened to 4096 numbers. Your code renders it at 256 by 256 with miniSD for the prompt "an astronaut riding a horse on mars".

CLIP ViT-B/32 scores each image once for the objective. The two measures are learned: DivProj, one linear layer, maps 512 CLIP image features to two coordinates.

Human feedback is simulated. DreamSim judges triplets of images, and DivProj trains so its distances agree.

So your code lane grows: at iterations 1, 21, 51 and 101 it adds 1000 triplets, fits a fresh DivProj, re-scores the current elites, and builds a new archive and scheduler.
