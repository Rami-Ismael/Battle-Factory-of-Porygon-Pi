Software licence fees are zero for these open-source paths; the real cost is conversion, sampler and attention work, numerical validation, and ongoing maintenance.

## Port work

Code/docs: oMLX means the Apple silicon inference server by jundot, with continuous batching and tiered key/value caching, not a different project with a similar name [S1]. The inspected engine pool recognizes `diffusion_gemma` as its diffusion family; the vision-language engine routes it to a serial diffusion lane [S2]. Thus “oMLX has no diffusion support” would be false. This support and its separate speculative block-diffusion drafter do not establish support for any of these seven full-attention candidates. Stock MLX LM has GPT-2, Qwen2, Qwen3 and Llama implementations; inspection found no `llada.py` or `dream.py` in its model directory [S3].

Code/docs: the GPT-2, Qwen2, Qwen3 and Llama forwards construct causal attention masks. Their tensor shapes are useful conversion starting points, not masked diffusion implementations [S3]. GPT-2 sanitation transposes Conv1D projection weights. The two masked Qwen checkpoints declare adapted model types rather than ordinary causal Qwen, so blindly passing them to the normal loader is insufficient. Their tied parameter totals are 494 million and 596 million; stored duplicate token matrices must not become accidental extra parameters [S4].

Code/docs: dLLM's masked diffusion language model sampler, `MDLMSampler.infill`, constructs a canvas from the supplied text and updates masks throughout it over repeated forwards. Its options include a reveal schedule, confidence-based selection, temperature, forbidden tokens, padding and optional classifier-free guidance; `right_shift_logits` changes alignment [S5]. Inference: port this loop to MLX instead of replacing it with MLX LM's one-token generation callback. Keep the original non-mask positions immutable, compute the complete bidirectional hidden state every step, gather mask-position hidden states before vocabulary projection, and sample/update on the device. Match the exact existing sampler configuration rather than assuming that all masked models use identical prediction alignment.

Code/docs: [MacPaw/Fast-dLLM-mlx](https://github.com/MacPaw/Fast-dLLM-mlx) provides Dream forward code, an uncached diffusion runner, and a fast runner using dual-cache approximation and threshold reveals [S6]. Its README demonstrates eight-bit DiffuCoder, a Dream-style coding model, not this exact Dream Base checkpoint. In the inspected uncached path, `diffusion_generate_step` calls `model(x, cache=prompt_cache)` without an attention mask. `DreamModel` fills a missing mask using MLX LM's `create_attention_mask`, which returns `"causal"` for sequence length greater than one [S6,S3]. Inference: the uncached default cannot certify bidirectional parity. Change that path to actual full attention. Passing `None` alone does not fix it because `None` triggers mask creation. The fast model handles `"full"` explicitly, but its generator rejects `dual_cache=False` [S6]. Its plain runner can start from a fixed masked canvas without appending tokens if maximum length equals canvas length, but sampler semantics and RNG seeding still differ from our working infill method.

Code/docs: [akkikiki/mlx-dlm](https://github.com/akkikiki/mlx-dlm) contains `models/llada.py` and `llada_generate.py`. Attention is explicitly bidirectional, and its loop repeatedly fills masks [S7]. However, the original Base index uses `model.transformer.blocks.*`, `model.transformer.wte.*`, `model.transformer.ln_f.*` and `model.transformer.ff_out.*` [S8]. The fork's sanitation looks for `.layers.` and does not translate these prefixes. Its argument class uses `hidden_size`, `num_hidden_layers` and `intermediate_size`, whereas original config uses `d_model`, `n_layers` and `mlp_hidden_size`. Defaults happen to match many Base dimensions; that is not conversion. Inference: fix both config and tensor-name translation, verify rotary embedding convention and all tensor shapes, and require strict load plus logit parity. Its default generation appends a masked suffix; a fixed-canvas infill entry point is still needed. There is existing iterative MLX code to reuse, but no verified MLX port of dLLM's exact `MDLMSampler` was located in this bounded search.

Code/docs: public MLX-community LLaDA Instruct fp16/eight-bit model cards claim conversion with MLX LM 0.21.0 [S9]. They are a different checkpoint, and current stock MLX LM lacks the architecture module. Upstream “Add LLaDA Diffusion Model Support” and “Add LLaDA 1.0/2.0 Diffusion Model Support” pull requests were both closed without merge [S10]. Inference: a conversion card or closed proposal is not proof of a maintained, working Base-model route.

Inference: exact autoregressive key/value caches cannot be reused across diffusion steps. Changing a mask changes attention inputs throughout the canvas, including deeper hidden states of the fixed text. oMLX's prefix cache, solid-state-drive cache and token-level continuous batching cannot remove those full forwards. A new diffusion-aware scheduler could combine canvases at a common step, but our equal-length, fixed-step queue can already use ordinary static batching. Approximate dual caches and threshold reveals are different algorithms needing separate quality comparisons, not backend-only speedups. Memory allocation-buffer reuse remains useful and is distinct from key/value reuse.

Inference, engineering planning rather than measured labour: one shared sampler/conversion/parity harness is roughly 3–6 engineer-days; small GPT adapters another 1–2 days together; masked Qwen adapters 1–3 days together; Dream 2–4 days; LLaDA 3–6 days; DiffuLLaMA 1–3 days. These overlap and are uncertain, not fixed quotes. An oMLX request type, scheduler, memory admission and result adapter could add another 3–7 days. Start with a single small Qwen port in plain MLX, avoiding server integration until speed and parity justify it. Retaining a fork adds version-pinning and regression work whenever kernels, loaders or samplers change.

## Memory

Measured in [“Benchmark each candidate's peak memory on the laptop” (#170)](https://github.com/Rami-Ismael/Battle-Factory-of-Porygon-Pi/issues/170): the 24 GB M4 Pro allows 19,069,665,280 bytes, or 17.76 GiB, under the agreed ceiling. PyTorch 2.15.0, Transformers 4.57.3, macOS 27.2. Dream mask-only peaks at 15.42 GiB for B1 and 16.49 GiB for B2; DiffuLLaMA mask-only peaks at 15.61 GiB for B4. LLaDA fails during allocator warm-up on a single 14.93 GiB buffer. Last logged memory before a failed allocation is not the peak needed to fit that run.

Code/docs: checkpoint tensor totals give bf16 weight floors of 0.232, 0.661, 0.920, 1.110, 14.185, 14.930 and 12.551 GiB in table order, counting tied Qwen matrices once [S4,S8]. MLX conversion supports an explicit dtype, and safetensors loading uses arrays rather than a Transformers-style reservation of one full-model warm-up tensor [S11]. Inference: a correct layer/tensor-wise loader avoids the specific single-buffer failure. MLX does not bypass Metal's individual-buffer restrictions. Avoid packing the entire model into one allocation and avoid holding two device copies during conversion. Confirm dtype explicitly: the [MLX data type reference](https://ml-explore.github.io/mlx/build/html/python/data_types.html) lists bf16 arrays, but availability does not verify this model's actual load peak or kernel correctness on this machine.

Inference: LLaDA Base should load in bf16 as individual arrays. Its weights leave 2.83 GiB for all other allocations. That is plausible for B1 at this short canvas, particularly with mask-only scoring, but it is not proof that the whole generation loop fits. A loader fix within PyTorch might also avoid the observed failure; this is not a memory advantage unique to MLX.

Inference, reproducible component sizing: one bf16 vocabulary tensor for 354 positions with vocabulary 151,936 costs `B×354×151936×2/2^30 = B×0.100 GiB`. Scoring all 666 positions costs B×0.188 GiB. One float32 probability buffer doubles those figures. Temperature noise, perturbed scores and sorting can add further overlapping arrays. LLaDA's 126,464 vocabulary gives 0.083 GiB per bf16 mask-only tensor per row. These computations omit activations. Feed-forward, attention, normalization, compilation and allocator buffers all matter; an eager attention matrix scales as `B×heads×length²`, while memory-efficient attention may avoid retaining it. Releasing each step's graph is essential in lazy MLX so that 128 graphs do not remain live.

Inference: table memory envelopes are deliberately broad **planning assumptions**, not empirically calibrated predictions. They use `weights + 0.5–1.5 GiB fixed runtime reserve + B×activation/sampling allowance`. The per-row allowances reserve roughly 6–16 bytes per scored vocabulary element for overlapping logits, probabilities, noise and selection, plus layer temporaries. At 354×151,936 elements this alone is about 0.30–0.80 GiB per row. Smaller GPT and DiffuLLaMA vocabularies need less; wider feed-forward layers need additional space. These allowances are assumptions to test, not sums derived from a live MLX graph. They assume no gradients, no key/value history, efficient full attention, evaluation and release every step, bounded allocator cache, tied Qwen weights and no guidance doubling. They exclude original PyTorch model residency, conversion duplicates and oMLX's other loaded models. Exhaustively materialized sorting, retained graphs or different allocator behaviour can exceed the envelope. At the optimistic edge the suggested larger batches fit; at the pessimistic edge some do not. No published exact-model MLX peak-versus-batch ladder was found, so **larger batches are possible, not established**.

Code/docs: MLX `set_memory_limit` is a guideline, not PyTorch's hard out-of-memory guard. Its documented default is 1.5 times the recommended working set, and allocations can use available swap [S12]. `get_peak_memory` measures allocator active allocations; it must not be equated silently with PyTorch driver allocation [S13]. Inference: a port is not acceptable merely because its default MLX run succeeds beyond 17.76 GiB. Track active plus cached memory, process residency and swap separately; apply a watchdog and conservative headroom, reject any run exceeding the ceiling, and do not change wired-memory system limits. Disable other oMLX models and persistent caches for a fair test.

## Speed

Measured in #170: our throughput changes little with batch size. Small GPT improves 7.5 to 6.6 seconds/team with full logits, or 6.1 to 5.0 mask-only. Coder-derived Qwen improves 20.8 to 18.7, Qwen3 28.8 to 27.9, Dream 225.7 to 220.3, and DiffuLLaMA 269.3 to 260.8 mask-only. Medium GPT's largest B64 is slower than B32, 16.46 versus 13.35 seconds/team. Inference: choose the fastest fitting batch for production; largest batch and highest throughput are different questions.

Code/docs: the prompt summary's shared 666-token/bf16 setting needs a correction from the actual #170 comments. Small and medium GPT ran fp16 with 662 tokens and 348 masks; DiffuLLaMA ran bf16 with 805 tokens and 420 masks. The Qwen and Dream rows used 666/354. Inference: keep those tokenizer-specific settings when comparing to historical rates. A separate uniform 666/354 synthetic tensor test can isolate backend differences but is not the exact same text for every tokenizer.

Inference: batching multiplies the work on a long, fully bidirectional canvas. At B1, 666 positions already form hundreds of matrix rows. This can saturate dense matrix compute without several teams at once, unlike single-token autoregressive decoding. The flat batch curves are consistent with this explanation, but no operator trace in #170 establishes it as the sole cause. Large vocabulary sampling, host synchronization and kernel shapes can also contribute. MLX may reduce dispatch/sampling overhead; it cannot eliminate 128 full-sequence evaluations under unchanged semantics.

Measured by the benchmark authors, with code inspected: [TristanBilot/mlx-benchmark](https://github.com/TristanBilot/mlx-benchmark) reports the following M4 Pro, 20 GPU-core, 24 GB results with MLX 0.24.1 [S14]. Average matrix multiplication is 9.81 ms MLX versus 13.28 ms MPS, a 1.35× ratio; compiled MLX is 6.86 ms, 1.94× versus MPS. Linear is 6.37 versus 6.20 ms, essentially equal with MLX slightly slower. Scaled dot-product attention is 2.62 versus 1.81 ms, MLX slower. The code uses float32 random inputs, forces completion in both backends and excludes the first of ten iterations. These are averages over shapes, not our denoiser, and the M4 Pro heading does not record the PyTorch version. Inference: useful counterevidence to a universal backend equality claim, weak evidence for a bf16 end-to-end improvement over PyTorch 2.15.0.

Measured by its author: [JialiangFan/mac_tflops](https://github.com/JialiangFan/mac_tflops) reports MLX general matrix multiplication on a 20-core M4 Pro with 48 GB: fp16 reaches 7.349 TFLOP/s at 4096-square and 7.447 at 8192-square; float32 reaches 6.528 at 4096 [S15]. The source warms up three iterations and evaluates every timed output, ten iterations. It does not provide bf16, MPS, exact laptop SKU matching or model forwards. Inference: `7.447/5.7 ≈ 1.31` makes a modest compute improvement plausible, but this is not a measured backend ratio. It refutes treating this project's measured 5.7 as an immutable ceiling for every library, dtype and shape. It does not refute that both libraries share the same physical GPU ceiling.

Code/docs: MacPaw compares Dream-style MLX variants and causal MLX coding models with different caching, step and quantization settings [S6]. Inference: these results establish an implementation lead, not MLX-versus-MPS team throughput. No directly matched M4 Pro bf16 666-token, full-attention denoising benchmark was found. Autoregressive decode tokens/second, quantized prompt caching and M5 neural-accelerator results cannot supply that missing measurement.

Inference: the table's neutral rate assumes equal amortized seconds/team after a correct port at its fitting batch. Its sensitivity range multiplies PyTorch throughput by 0.7 and 1.3, representing a possible regression or modest improvement. This is an explicit budgeting scenario, **not an expected-value estimate or evidence-backed bound**; gains or losses outside it remain possible. Actual teams/hour at the largest MLX batch is unknown for every candidate. LLaDA has no comparable bf16 baseline: using roughly 7 billion non-embedding parameters, 666 tokens, 128 steps and 5.7 TFLOP/s gives about 209 seconds/team from dense projections alone, ignoring attention, vocabulary/sampling and any guidance. The roughly 17 teams/hour reciprocal is only an idealized compute bound under those assumptions, not a throughput promise.

Inference: evidence supports testing MLX for modest improvement, not migrating for a claimed speedup. Ported small Qwen is a useful first test because its tiny weight footprint makes full-precision parity practical. Keep quantization a separate comparison: the prior [quantization report](https://github.com/Rami-Ismael/Battle-Factory-of-Porygon-Pi/blob/research/quantization-masked-diffusion/code/docs/research/quantization-masked-diffusion.md) and #170 indicate that saving weight memory did not establish a time saving in this compute-heavy regime. MLX quantized kernels must earn their own measured verdict.

## Proposed benchmark

Inference, proposed only: run after the generation queue has released the GPU and this research has been reviewed. Do not benchmark alongside another session. Reuse local checkpoint files; do not auto-download models. Keep current PyTorch baseline results as historical measurements; a short matched control later is justified because the external comparisons use old software and different shapes.

1. **Bidirectional parity check** `bidirectional_parity`: begin with coder-derived masked Qwen. Port full attention and `MDLMSampler.infill`; compare logits on the same fixed canvas before generation. Changing the last token must influence the first mask, while initial non-mask tokens must remain unchanged after sampling. Check shapes, dtype, tied matrices, forbidden tokens, right-shift settings and seeded probability distributions. GPU arithmetic and RNG differ, so do not require byte-identical random samples. Also run deterministic choices and report top-token agreement and probability divergence. For Dream, verify shifted hidden-state selection before mask-only vocabulary projection. For LLaDA, strict-load every original tensor after explicit remapping.
2. **Matched forward timing** `matched_forward`: identical cached input token IDs, no gradients, full attention, no key/value reuse, 666 tokens/354 masks where historical tokenizer permits, 128 denoising steps, temperature 1, seed 2026, no extra classifier-free guidance. Preserve historical 662/348 fp16 GPT and 805/420 bf16 DiffuLLaMA comparisons separately. Test full logits and mask-only logits. Separate matrix projections, attention, vocabulary scoring and sampling time. Warm up and synchronize both backends. Compare uncompiled with compiled MLX as separately named runs; include compilation latency outside steady-state time.
3. **Batch memory ladder** `batch_memory`: one fresh process per B=1,2,4,…; a single step first, then all 128 if safe. Stop early using conservative projected next-allocation bounds and a memory watchdog. Set MLX cache limits explicitly, request a 19,069,665,280-byte memory guideline, but never mistake it for a hard cap. Record loading peak, synchronized active/peak and cached allocation, operating-system residency, swap change and per-step maxima. Reject a setting that exceeds the agreed ceiling or swaps, even if it finishes. Record largest batch and fastest fitting batch separately.
4. **Legal team throughput** `legal_team_rate`: three complete timed batches per safe setting after one warm-up, exact same team text and legality validator, no repair. Report wall seconds/team drawn, teams drawn/hour, accepted share and legal teams/hour. Check that names, requested fixed values and Stat Points remain intact. Approximate caching, fewer steps and quantization get separate runs only after a backend-only comparison, because they can change output quality.

Proposed script outline, not executed:

```python
# worker --backend mlx|mps --model ... --batch B --scope masks|all
# Resolve local weights; enforce process/allocator accounting before allocation.
model, tokens, fixed_positions = load_and_validate_local_inputs()
# Capture load peak. Warm-up is separately timed and accounted.
for run in range(4):  # warm-up + three timed batches
    x = tokens.copy()
    synchronize_backend()
    start = monotonic()
    for step in range(128):
        hidden = bidirectional_forward(model, x, cache=None)
        logits = project_selected_positions(hidden, alignment, scope)
        x = matched_mdlm_update(x, logits, step, fixed_positions)
        evaluate_and_release_step_graph(x)
        check_memory_and_swap_or_abort()
    synchronize_backend()
    record(monotonic() - start, peak_memory, validate_teams(x))
# throughput = 3600 * B / batch_seconds; legal throughput multiplies acceptance.
```

Inference, runtime budget at current PyTorch rates: a small-Qwen B1 three-run timing is about one minute plus warm-up. A full small-Qwen B1–16 ladder with one warm-up plus three batches per setting is about 40 minutes; GPT small through B32 about 20–30 minutes; Dream B1 and B2 about 45 minutes; DiffuLLaMA through B4 about two hours. Backends tested twice roughly double these budgets; LLaDA runtime is unknown and should begin with a capped single-forward check. These estimates count batch wall time as B×seconds/team; multiplying by B again when reporting teams/hour would be wrong. Bound memory trials first so failed large batches do not consume a complete 128-step run.
